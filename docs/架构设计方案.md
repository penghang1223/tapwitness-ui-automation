## 1. 项目定位与设计目标

### 1.1 一句话定义

TW（Test Workflow）是一个 **Claude Code plugin**：把「UI 自动化测试开发」做成一条跨项目、跨技术栈可复用的**流程流水线**。命令恒定（`/tw:*`），技术栈差异由**域包**吸收，项目差异由 **profile** 吸收。

### 1.2 要解决的问题

UI 自动化开发的老问题不是"不会写 Playwright 代码"，而是：

| 问题 | 本框架的答案 |
|---|---|
| 每个项目从零摸索业务知识、数据、定位符，经验无法复用 | 8 阶段活动模型 + 域包作业手册 + profile |
| AI 凭想象猜定位符、猜边界值，产出假绿用例 | **证据门控**：没依据不生成用例，没真实 DOM 不写定位符 |
| 知识散落在个人脑子里，踩过的坑反复踩 | 坑点三层路由 + 域层反馈队列 + 已吸收注册表 |
| 流程靠自觉，质量门靠人盯 | 状态机 + Exit Gate 五步 + 校验器把不变量变成可执行断言 |
| 不同 Claude Code 会话之间上下文丢失 | 磁盘状态文件是唯一真相源，跨会话可恢复 |

### 1.3 三层架构（核心）

```
L0  流程内核（换项目、换栈都不变）
    skills/ + tw/protocols/ + tw/tools/ + tw/templates/
    31 个 /tw:* 命令 + 两套状态机协议 + 校验器 + 生成器

L1  域包（换栈换域包）
    tw/packs/<pack_id>/
    每技术栈一本「8 阶段作业手册 + 坑点库 + 工具实现」

L2  项目适配层（换项目换 profile）
    <宿主项目>/.claude/project_profile.md
    <宿主项目>/.claude/profiles/<subsystem>.md   （多子系统仓库）
    目录/命令/数据层/知识库/项目约定/项目坑点表
```

**依赖方向是单向的**：L0 可以引用 L1 的**契约**（pack.yaml 的字段），但不得引用任何具体域包内容；L1 可以引用 L0 协议，但不得写 L0 的状态文件；L2 只被读取，不含框架逻辑。

### 1.4 两条独立工作流（刻意分开，禁止合并）

框架内置两条**零耦合**的工作流，各自有状态机、状态目录、看板、协议、校验器：

| | 8 阶段工作流 | 录制驱动工作流 |
|---|---|---|
| 起点 | 业务知识召回（读 KB + 页面） | 人工录制一条真实流程 |
| 阶段数 | 8（`current_stage` 1..9，9=完成） | 5（`current_stage` 1..6，6=完成） |
| 状态目录 | `.claude/workflows/` | `.claude/record-workflows/` |
| 状态文件 | `state.json` | `record_state.json` |
| 协议 | `tw/protocols/*` | `tw/workflows/record-driven/protocols/*` |
| 分发器生成器 | `tw/tools/gen_dispatchers.py` | `tw/workflows/record-driven/tools/gen_record_dispatchers.py` |
| 校验器 | `tw/tools/validate_workflow.py` | `tw/workflows/record-driven/tools/validate_record_workflow.py` |
| 入口命令 | `/tw:new-feature` | `/tw:record-feature` |
| 代码审核 | 审"写码前的 plan" | 审"跑通后的最终代码"（独立子代理） |

> **这是刻意的架构决策，不是历史包袱**：两条工作流的失败模式、回拨语义、审查对象都不同。合并会同时牺牲两者的质量门。重建时**不要**为了"消除重复"而抽象出统一状态机。共享的只有 L0 方法论协议（`assertion-protocol.md`、`case-expansion-protocol.md`、`dump-artifact-protocol.md`），且是**文档级复用**，不是代码级耦合。

### 1.5 十条设计原则（重建时的判据）

1. **命令恒定，做法下沉**：`/tw:verify` 在 Web/iOS/Android 下名字一样，做法由域包给。
2. **薄分发器**：每个阶段 SKILL.md 只做五步编排，真正的门禁逻辑在协议文件里（单一真相源）。
3. **状态只有一个写者**：只有 Exit Gate 能推进状态；域包阶段指令禁止写 `state.json`/`.current`/`dashboard.md`。
4. **不猜**：定位符要有真实 DOM 依据；边界/负面用例要有 `evidence`；DB 字段要先 `DESCRIBE`。
5. **双格式产出**：人读 `.md` + 机读 `.json`，下游阶段强制从磁盘重读。
6. **能力键门控**：skill 通过 `pack.yaml.auxiliary` 的键是否存在判断功能可用性，**不硬编码域包白名单**。
7. **不变量可执行**：能用脚本校验的规则一律写成校验器，而不是写在文档里靠自觉。
8. **防漂移**：分发器由生成器产出，`--check` 做 diff；文档间引用契约由校验器检查。
9. **反馈闭环**：域层坑点进项目内待提交队列 → 维护者合入域包 → 发版全员共享，绝不直接改 plugin 缓存。
10. **失败要留证据**：截图 + DOM + 日志落盘，归因先于修复。

## 2. 技术选型与运行环境

| 项 | 选择 | 约束 |
|---|---|---|
| 宿主 | Claude Code plugin | 依赖其 Skill 机制（`skills/<name>/SKILL.md` + YAML frontmatter） |
| 框架内容载体 | Markdown（指令）+ YAML/JSON（契约） | 不含可执行运行时逻辑，AI 按指令执行 |
| 工具脚本 | Python 3.8+ | 仅用标准库；`PyYAML` 用于解析 pack/profile（缺失时相关校验会失败，应视为必装） |
| 编码 | 全仓库 UTF-8 | Windows 控制台默认 GBK，所有脚本启动时必须 `sys.stdout/stderr.reconfigure(encoding="utf-8", errors="replace")` |
| 版本管理 | git + tag | 版本号是唯一发布开关（§3.1） |
| 测试 | 无单元测试框架 | 用校验器 + `--check` 模式 + 临时 fixture 目录做验收 |

**不引入**：数据库、Web 服务、依赖注入框架、构建打包步骤。整个 plugin 仓库就是可分发的产物。

### 3.2 plugin 与 marketplace manifest

`.claude-plugin/plugin.json`：

```json
{
  "name": "tw",
  "description": "<一句话 + 命令清单 + 域包清单；用于 marketplace 展示>",
  "version": "1.31.0",
  "author": { "name": "<维护者>" }
}
```

`.claude-plugin/marketplace.json`：

```json
{
  "$schema": "https://anthropic.com/claude-code/marketplace.schema.json",
  "name": "tw-marketplace",
  "description": "TW 工作流框架市场（单仓库模式：marketplace 与 plugin 同仓库）",
  "owner": { "name": "<维护者>" },
  "plugins": [
    {
      "name": "tw",
      "description": "<简述>",
      "source": "./",
      "category": "testing"
    }
  ]
}
```

规则：
- `plugin.json.version` 是**唯一发布开关**；不涨版本，`claude plugin update` 不会拉取新内容。
- `description` 只是展示文案，是最容易漂移的地方（源码里"录制驱动 8 个"是笔误：实际有 9 个 `record-*` 目录，其中 `record` 是独立工具）。**以 §3.3 的表格为准**，重建后可用脚本对比 `skills/` 目录数与描述中的数字。
- `marketplace.json.source` 指向仓库根（`./`），使同一仓库同时充当 marketplace 与 plugin。
- 安装命令：`claude plugin marketplace add <仓库地址>` → `claude plugin install tw@tw-marketplace`。

### 3.5 SKILL.md 契约

每个 skill 是一个目录，内含 `SKILL.md`，YAML frontmatter 必填两项：

```markdown
---
name: <命令名，与目录名一致>
description: >
  <一句话定位>。<适用/触发关键词：……>
---

# /tw:<命令名> — <标题>

...正文...
```

规则：
- `description` 决定模型何时触发该 skill，必须写清**触发词**（中文 + 英文）。
- 生成的分发器 description 统一带 `[TW 阶段N]` 前缀（8 阶段）或 `[TW 录制阶段N]`（录制）。**8 阶段生成器**把该前缀当作覆盖护栏依据（带前缀却不在 `STAGES` 里的 skill 判为漂移）；**录制生成器当前不检查该前缀**，所以它只是命名约定（重建时建议补上检查）。
- 分发器正文固定含一句框架定位：`本 plugin 根目录下的 tw/ 子目录（相对本 SKILL.md 为 ../../tw/）；路径不确定就 Glob 搜 **/tw/protocols/gate-protocol.md`。这是为了让安装到 plugin 缓存目录后的路径解析不依赖绝对路径。

### 3.6 域包版本基线

| 域包 | version | min_core_version | 状态 |
|---|---|---|---|
| `playwright-python` | 1.10.0 | 1.0.0 | 实战验证；录制工作流唯一支持者 |
| `ios-appium` | 1.3.0 | 1.1.0 | 已实现，录制未实现 |
| `android-airtest` | 1.3.0 | 1.2.0 | 已实现，录制未实现 |
| `android-appium` | 1.3.0 | 1.5.0 | 已实现，录制未实现 |

录制工作流定义 `workflow.yaml` version 1.1.0。

**版本语义（重要）**：当前源码中 `min_core_version`、profile 模板的 `core_version` **没有任何消费方**（无校验器读取、无运行时比较），属于**展示性元数据**。重建时：
- 保留字段，避免破坏 schema；
- **不要**新增基于它们的强制校验（会与存量 profile 冲突：模板默认 `core_version: 1.4.0` 低于 `android-appium` 的 `min_core_version: 1.5.0`，这是源码既有矛盾）；
- 真正的发布开关只有 `plugin.json.version`。

## 4. 运行模型（一次命令从触发到退出）

### 4.1 分发器五步（所有阶段命令的统一骨架）

```
Step 1  Gate Check      读 .current → state.json，四分支校验 current_stage
Step 2  解析 profile     两级 profile（子系统 / 仓库级）+ 端解析（pack_by_platform）
Step 3  加载域包         pack.yaml → stages.N.file + references + pitfalls.md
Step 4  执行阶段指令     按域包做实际工作
Step 5  Exit Gate        五步收尾（写产出→审查门→更新状态→坑点路由→刷看板+校验）
```

**Step 1 Gate Check 四分支**（`current_stage` 记为 C，本命令阶段号记为 N）：

| 分支 | 条件 | 行为 |
|---|---|---|
| a | C < N | 拒绝："请先完成阶段 C" |
| b | C > N 且阶段 N 为 `done` | 提示已完成；重跑需先改产出并手动重置 |
| b' | C > N 且阶段 N 为 `skipped` | 提示"阶段 N 已被 bypass"，拒绝重跑；需先移除 `bypasses` 记录并重置状态 |
| c | C == N 且 status ∈ {pending, failed} | 置 `in_progress`（写 started_at），继续 |
| d | C == N 且 status == in_progress | 继续（恢复中断） |

> 分支 b' 是对源码的**补齐**：源协议只写了 `done`，但 `bypass` 之后重跑被跳过的阶段是真实存在的组合，不定义会让实现者各写各的。C == N 且 status 为 `done`/`skipped` 在自洽规则下不可能出现，无需处理。

特殊分支：
- 8 阶段：`C==4` 且 `4_case=done` 且 `5_verify=failed` → 视同分支 c，重跑阶段 5。
- 录制：`C==3` 且 `3_case=done` 且（`4_run=failed` **或** `5_review=done`）→ 视同分支 c，重跑阶段 3（这两者都是"已回拨"状态）。
  `5_review=failed` **不在**此列——它表示审核链路失败、未回拨，`current_stage` 停在 5，修复审核能力后直接重跑 `/tw:record-review`（分支 c 处理 C==5 的 failed）。

### 4.2 profile 解析（两级 profile + 端解析）

**profile 只有两级**（源码分发器标题写"三级"，但正文只定义了两级；重建时按下面的两级实现，不要为凑"三级"发明第三个 profile 文件）：

```
第一级：feature 带上 subsystem 且 .claude/profiles/<subsystem>.md 存在
        → 用子系统 profile
第二级：否则用仓库级 .claude/project_profile.md（单栈仓库或兜底默认）
两者都缺 → 停止，引导 /tw:project-scan
```

**端解析（混合子系统）**：

```
feature.state.json 有 platform 字段 且 profile 有 pack_by_platform？
  ├─ 是 → pack = pack_by_platform[platform]；读「项目约定（<platform> 端）」小节
  └─ 否 → pack = profile.pack；读平铺「项目约定」
```

同时记录：`paths`、`run`、`data_layer`、`kb`、`external_sync`、项目坑点表。`kb`/`external_sync` 始终从仓库级 `project_profile.md` 读（子系统 profile 不重复定义）。

### 4.3 Exit Gate 五步（缺一不可）

**Step 1 写产出物**
按 `pack.yaml.artifacts.<N>`（录制为 `workflow.yaml.artifacts.<N>`）写文件到 feature 目录。文本产出文件末尾固定两节：`## Skill 回写记录`、`## 人工介入记录`。JSON 产出保持合法 JSON。

8 阶段的阶段 1、3 和录制驱动的阶段 2，先按各自 gate protocol 运行 `tw/tools/validate_artifacts.py`，校验本次结构化产物后再进行审查和状态更新。阶段 3 在存在阶段 1 用例清单时对账断言的 case_id；清单缺失时告警。历史已完成阶段不因新增校验而被自动回溯阻断。

**Step 2 审查门**
强制审查门的阶段：8 阶段为 1（用例清单）/3（断言）/4（plan）；录制为 2（用例清单）/5（代码审核），阶段 3 的暂停在内部 3a。

| 调用方 | mode | Exit Gate 行为 |
|---|---|---|
| 单阶段命令 / `workflow-next` | manual | 暂停等用户确认；用户动作后按下方"三值模型"写状态 |
| `auto` / `record-auto` | semi-auto | 不暂停；置 `review_needed=true` 后继续；auto 在出口展示 UI 并回写状态 |
| `auto-full` / `record-auto --full` | full-auto | 不暂停；置 `review_needed=true`；无人审查，保持 `true` |

**审查门状态的三值模型（唯一裁决，防止实现漂移）**

Exit Gate Step 2 在**非 manual** 模式下先把"本次审查门尚未被人工当场审查"记为 `review_needed=true`；之后按用户动作回写：

| 用户动作 | `human_intervention` | `review_needed` | `intervention_note` |
|---|---|---|---|
| `[Enter]` 批准 | `false`（未修正） | `false`（已审） | `null` |
| `[edit]` 修改后重展示 | `true` | `false` | 写清改了什么 |
| `[skip]` 跳过此门 | `true` | `false` | 写"用户选择跳过审查" |
| `[accept]` 放行（录制阶段 5） | `true` | `false` | 写裁定理由 |
| `[exit]` 退出 | 保持退出前的值，已完成阶段为 `false` | 保持 `true` | 保持原值 |
| full-auto 从未展示 | `false`（AI 独立） | `true` | `null` |

> 注意 `[Enter]` 批准**不算**人工介入（用户没有修正/补充/否决），所以 `human_intervention=false`；但门确实被审过，所以 `review_needed=false`。`[skip]` 虽然放行，但用户行使了判断权，记 `true` + note。
> 手动模式的审查门没有这个中间态：暂停即当场审，直接按上表第一/二/三行写。

**Step 3 更新状态**

```
stages.<key>.status = done
stages.<key>.completed_at = now
stages.<key>.human_intervention = true/false
current_stage = N+1
stages.<N+1>.status = in_progress, started_at = now   （仅当 N < 完成值-1）
```

**完成值**：8 阶段为 9，录制为 6（源码里录制写作 `state.max_stage: 6`，8 阶段无该字段、直接按 9）。
最后一个阶段完成时只把 `current_stage` 置为完成值，**不要**创建第 9 个 / 第 6 个阶段键。

失败路径（**按 mode 分支，四套独立规则**）：

| 场景 | mode | 状态变更 | 是否回拨 / 计数 |
|---|---|---|---|
| 8 阶段 5，7 轮用尽 | manual / semi-auto | `5_verify=failed`，`current_stage=4` | 回拨到 4；提示 `/tw:ui-test-diagnosis` |
| 8 阶段 5，7 轮用尽 | full-auto | `5_verify=failed`，`current_stage` 停在 5 | 不回拨；**停止推进并报告**（不继续阶段 6） |
| 录制 4，7 轮用尽 | manual / semi-auto | `4_run=failed`，`current_stage=3`，`3_case.status=in_progress` | 回拨到 3；`rework_round += 1` |
| 录制 4，7 轮用尽 | full-auto | `4_run=failed`，`current_stage` **保持 4**（自洽：首个非 done/skipped 就是 4） | **不回拨，`rework_round` 不变**；停止推进 |
| 录制 5，结论「需修」 | manual / semi-auto / full-auto | `5_review=done`，`current_stage=3`，`3_case.status=in_progress` | 回拨到 3；`rework_round += 1`；full-auto 同样自动回拨，受上限约束 |
| 录制 5，审核链路本身失败 | 任意 | `5_review=failed`，`current_stage` **保持 5** | 不回拨、不计数；停止并报告 |

> `rework_round` 的语义严格是"**回拨进入阶段 3 的次数**"。没有发生回拨就不加一（所以 full-auto 阶段 4 用尽、以及 5_review=failed 都不计数）。
>
> **8 阶段 full-auto 的一处源码矛盾与裁决**：源码 `auto-full` 说阶段 5 失败后"继续推进阶段 6"，但 `current_stage = 第一个非 done/skipped 的阶段号`，5 既然 failed，`current_stage` 只能是 5——继续推进会让状态文件非法。**重建裁决：记录 `failed` 后停止推进并报告**。确实想跑回归时，只能显式把 5_verify 置 `skipped` 并写 bypass 记录（留审计），不能靠"failed 着往下走"。

**Step 4 坑点三层路由（强制，无新增也要显式写"本阶段无新增坑点"）**

```
Q1 换一个同技术栈的项目，它还会出现吗？
   否 → 【项目层】写入 .claude/project_profile.md「项目坑点表」
   是 → Q2
Q2 换一个技术栈，它还会出现吗？
   否 → 【域层】追加到 .claude/tw_feedback.md（待提交队列）
        禁止直接改 plugin 缓存里的 pack pitfalls.md（升级会丢失）
   是 → Q3
Q3 是业务语义/流程规则吗？
   是 → 【业务层】KB（按 profile.kb.writeback: auto|manual|off）
   否 → 不入库，仅记入当次阶段产出
```

行格式：
- 项目层：`| 日期 | 阶段 | 现象 | 根因 | 对策 |`
- 域层多两列：`| 日期 | 阶段 | 现象 | 根因 | 对策 | 适用平台 | 状态(待提交) |` + 来源 feature

若本阶段有域层入队，**必须**打印：
```
✓ 域层坑点已入队 .claude/tw_feedback.md（当前队列 N 条待提交）
```

**Step 5 刷新 dashboard + 运行校验**

dashboard 头部固定正则：
```
**X / N 完成** | **Y 进行中** | **Z 未启动**
```
分桶：已完成 / 进行中（按阶段倒序）/ 未启动；`_template` 不计入功能数。

然后运行非 strict 校验器；有新 warning 当场处理。

### 4.4 自动推进模式

| 命令 | mode | 暂停点 | 异常处理 |
|---|---|---|---|
| `new-feature` + `workflow-next` | manual | 每阶段出口 | 用户逐段驱动 |
| `auto` | semi-auto | 阶段 1/3/4/5 出口 | 阶段 5 失败让用户选 fix/skip/exit |
| `auto-full` | full-auto | 无 | 阶段 5 失败 → 记录 `failed` 并停止推进（源码写"继续阶段 6"，但与 state 自洽规则冲突，见下方裁决） |
| `continue` | 读 state | 同原 mode | 从 `current_stage` 恢复 |
| `record-feature` + 单阶段命令 | manual | 阶段级 | — |
| `record-auto` | semi-auto | 阶段 1e / 2 出口 / 3a / 5 出口 | 回拨感知，超限停止 |
| `record-auto --full` | full-auto | 无（不等待用户） | **3 类必须停 + 2 类确定性处理**（§7.3）；"停"= 终止推进并报告，不是暂停等输入 |

**Exit Gate 级审查门**统一四选项：`[Enter] 继续` / `[edit] 修改后重展示` / `[skip] 跳过此门` / `[exit] 退出`。
阶段内部子步骤的选项不同：录制 1e 只有 `Enter/edit/exit`（没有 skip）；录制阶段 5 是 `Enter/fix/accept/exit`（fix=回拨，accept=放行）。

**`[skip]` 跳过的是"这道审查门"，不是"这个阶段"**——这是最容易实现错的地方：
- **两条工作流一致**：审查门的跳过**不写 `bypasses`**。`bypasses` 只记阶段级跳过（与 `status: skipped` 一一对账，由校验器检查）。
- 状态回写按 §4.3 的"三值模型"：批准 → `false/false`；edit/skip/accept → `true/false` + note；exit 保持原值及 `review_needed=true`，已完成阶段保持 `false/true`；full-auto → `false/true`。
- 8 阶段源码的 `auto/SKILL.md` 曾写"记录 bypass"，与 `state-protocol` 的"bypasses ↔ skipped 双向对账"冲突；**重建时以 state protocol 与校验器为准**，不要复制那句措辞。
- 阶段 5（录制）另有 `[fix]`（回拨阶段 3）与 `[accept]`（用户裁定放行，记 note，**不写 bypasses**）。

**暂停机制分两类，不要混用**：
1. **Exit Gate 级审查门 / 自动模式暂停点**：Exit Gate Step 2 读 `state.json.mode`；manual 当场暂停，非 manual 先记 `review_needed=true` 不暂停。**暂停由 auto skill 在 Exit Gate 完成后统一展示**，不要在阶段 skill 里重复实现。
2. **阶段内部子步骤门（录制 1e / 3a）**：不在 Exit Gate。**UI 由阶段指令展示**；`record-auto` 只负责在循环里**不跳过**这两个点：
   - manual：阶段指令暂停；
   - semi-auto：`record-auto` 把 1e / 3a 当作暂停点（与阶段 2 / 5 出口同级），阶段指令展示 UI，`record-auto` 等待用户输入后继续；
   - full-auto：不暂停，阶段指令记 `review_needed=true`。
   > 这里 semi-auto **会停**（停在 1e/3a），不要套用"非 manual 一律只记不暂停"——那条只适用于 Exit Gate 级审查门。

### 4.5 两种工作流的命令边界

| 想做的事 | 走哪个 |
|---|---|
| 从零理解业务再开发 | 8 阶段 `/tw:new-feature` |
| 已能手工跑通一条流程，想派生整套用例 | 录制 `/tw:record-feature` |
| 给已有用例加测试点 | 直接 `/tw:ui-test-case` |
| 基于已开发完成的用例派生新场景 | `/tw:ui-test-extend` |
| 修 bug / 调试失败 | `/tw:ui-test-diagnosis` |
| 只想录一段代码骨架 | `/tw:record`（不进状态机） |

### 5.4 `state.json`（8 阶段）

```json
{
  "feature": "<feature_name，必须与目录名一致>",
  "created": "<ISO-8601>",
  "mode": "manual",
  "current_stage": 1,
  "stages": {
    "1_business":    { "status": "in_progress", "started_at": "<ISO-8601>", "human_intervention": null, "intervention_note": null },
    "2_data":        { "status": "pending", "human_intervention": null, "intervention_note": null },
    "3_assertion":   { "status": "pending", "human_intervention": null, "intervention_note": null },
    "4_case":        { "status": "pending", "human_intervention": null, "intervention_note": null },
    "5_verify":      { "status": "pending", "human_intervention": null, "intervention_note": null },
    "6_e2e":         { "status": "pending", "human_intervention": null, "intervention_note": null },
    "7_report":      { "status": "pending", "human_intervention": null, "intervention_note": null },
    "8_kb_feedback": { "status": "pending", "human_intervention": null, "intervention_note": null }
  },
  "bypasses": [],
  "_schema_notes": { "<自文档，可保留>" : "<说明>" }
}
```

可选顶层附加字段：`subsystem`（多子系统归属）、`platform`（混合子系统内的端）。

规则：
- `current_stage`：1–9 整数；9 = 全部完成。**自洽**：等于第一个 status ∉ {done, skipped} 的阶段号。阶段 5 失败按 §4.3 处理，manual / semi-auto 在前 3 阶段完成或跳过时回拨至 4，full-auto 正常停在 5；如存在更早的未完成阶段则以该阶段为准。
- `status`：`pending|in_progress|done|skipped|failed`。
- `human_intervention`：布尔三态 `true/false/null`，**禁止字符串**。规范：done/skipped 不得为 null（校验器 ERROR）；pending 应为 null（校验器只报 **WARNING**）；`in_progress` 保持 null（尚未产生介入记录，校验器不校验）；true 时必须写 `intervention_note`（校验器 ERROR）。审查门动作与三值的对应见 §4.3。
- `.current` 文件内容按 `strip()` 后与 feature 名精确比较；允许行尾换行（Windows 的 `\r\n` 也一样）。
- `failed` 只应出现在 `5_verify`（其他阶段出现只报 **WARNING**，不是拒收）。
- `review_needed`（可选 bool，**写在阶段条目上**，不在模板里预置）：非 manual 模式下"审查门尚未被人工审查"的标记，按 §4.3 三值模型回写（批准 → `false`；edit/skip/accept → `false` 且 `human_intervention=true`；full-auto 保持 `true`）。字段出现时校验类型。
- `bypasses[]`：`{stage:int, reason:str(≥5字符), timestamp:ISO-8601}`，与 `skipped` 双向对账。**只记阶段级跳过**；审查门的跳过不写这里（见 §4.4）。
- 只允许 Exit Gate 推进；禁止手改（例外：workflow-bypass 按协议改）。

### 5.5 `record_state.json`（录制驱动）

```json
{
  "feature": "<feature_name>",
  "workflow": "record-driven",
  "created": "<ISO-8601>",
  "mode": "manual",
  "current_stage": 1,
  "stages": {
    "1_capture": { "status": "in_progress", "started_at": "<ISO-8601>", "human_intervention": null, "intervention_note": null },
    "2_casegen": { "status": "pending", "human_intervention": null, "intervention_note": null },
    "3_case":    { "status": "pending", "human_intervention": null, "intervention_note": null },
    "4_run":     { "status": "pending", "human_intervention": null, "intervention_note": null },
    "5_review":  { "status": "pending", "human_intervention": null, "intervention_note": null }
  },
  "bypasses": []
}
```

附加规则：
- `workflow` 恒为 `"record-driven"`（校验器据此识别文件归属）。
- `current_stage`：1–6；6 = 全部完成。
- `failed` 只允许出现在 `4_run` / `5_review`。
- `review_needed`（可选 bool）：非 manual 模式下审查门尚未被人工审查时置 true，**不写 bypasses**；用户批准/edit/skip/accept 后按 §4.3 三值模型回写（批准清为 false，skip/accept 也清为 false 但记 `human_intervention=true`）。
- `rework_round`（可选 int，**首次回拨时才写入 `3_case`**，模板/初始状态不含）：回拨进入阶段 3 的次数，阶段 4 失败与阶段 5「需修」共用；>2 停止推进。
- `bypasses` **只记阶段级跳过**（与 `status: skipped` 对账）；审查门的 `[skip]`/`[accept]` 不写这里。

**`5_review=failed` 的语义缺口（源码未定义，本规格补齐）**：正常审核结论"需修"写 `5_review=done` + 回拨阶段 3；`failed` **只**保留给**审核动作本身没能完成**——独立子代理启动失败、审核产物不完整、审核所需输入缺失。此时置 `failed`、`current_stage` 停在 5、停止推进、提示人工介入，**不自动回拨、`rework_round` 不变**。

> 前置检查（`stage4_run.log` 非 PASS）**不属于** `5_review=failed`：阶段 5 的 5-0 步骤发现未跑通时，不进入审核、不写 `stage5_review.md`、状态保持 `in_progress`，直接提示回阶段 4 重跑。把"运行没跑通"记成"审核失败"会掩盖真实原因。

**`current_stage` 自洽**：等于第一个 status ∉ {done, skipped} 的阶段号；全部终态则为 6。`4_run=failed` 不参与回拨（停在 4 时自洽）；`5_review=done` 但已回拨时，`current_stage` 由 `3_case.status=in_progress` 决定，为 3。

`references` 的路径基准是**三类（四种写法）**，全部相对「激活域包目录」解析：

| 写法 | 基准 | 用途 |
|---|---|---|
| `workflows/record-driven/...` | 域包根 | 该栈的录制阶段指令与检查清单 |
| `references/...` | 域包根 | 参考手册 |
| `tools/...` | 域包根 | 工具实现文档（如 `tools/record.md`） |
| `../../protocols/...` | 框架 L0 | 复用 `tw/protocols/` 下的共用协议（如 case-expansion） |

声明原则：阶段「前置输入」中的**必读依赖**必须声明；标注"可选"的不声明，由阶段指令按需读取。

硬规则：

### 6.1 槽位定义（`tw/protocols/stage-registry.md`）

| 4 | `4_case` | 用例开发 | `ui-test-case` | DOM 分级采集 → plan（审查）→ 编码 | `stage4_plan.md` + `stage4_files.md` |
| 5 | `5_verify` | 本地验证 | `verify` | 首跑 + 探查-修复循环 ≤7 轮 | `stage5_verify.log` |

### 6.2 阶段 1 的三道门（最容易做错，必须精确实现）

1. **前置确认门（第 0 步，召回之前）**：列出 profile 实际值（`kb.path` 含 none/失效、`paths` 存量代码检索范围、`data_layer` 概要），问用户有无额外材料（PRD/需求/接口文档），回显被测模块/页面/功能点范围。manual 模式暂停等确认，**确认前不开始召回**。非 manual 记 `review_needed=true`，full-auto 产出顶部标注「⚠️ 召回范围未经用户确认」。
2. **实质缺口门（第 4 步，条件触发）**：把依据分为 已确认 / DOM 推断 / UNKNOWN / CONFLICT / 资料缺失；影响用例派生的缺口暂停问用户，选项 `[provide]`/`[confirm]`/`[single]`。
3. **用例审核门（第 6 步，强制）**：展示 编号/标题/类别/依据/证据级别/优先级/AI 建议，逐条 `[keep]/[merge]/[delete]/[edit]`；AI 必须主动给合并/删除建议。非 manual 时产出顶部标注「⚠️ 用例清单未经用户审核」。

**三道门在自动模式下的归属**：semi-auto 的 `/tw:auto` 在阶段 1 出口统一暂停，**同时补做**前置确认与用例审核；用户确认后，阶段条目上的 `review_needed` 按 §4.3 三值模型清零（edit/skip 记 `human_intervention=true`）。full-auto 不停、不补，`review_needed` 保持 `true`，产出顶部两个 ⚠️ 标注都要写。

### 6.3 阶段 4 的 4-pre 与 4a-0

- **4-0 重复性检查**：写代码前，中英双语并行搜索 `profile.paths.test_root`（测试文件名关键词 + PO 英文类名），命中即提示重叠。
- **4-pre DOM 分级采集**（不全部硬采）：缓存/存量 PO 命中 → 免采；断言密集的新页面 → MCP 自动导航/脚本主动采集写入 `page_cache/`；其余 → 延后标注，由阶段 5 按需补采。
- **4a-0 DOM 冲突对照**：用已采集的真实 DOM 逐条对照 stage3 断言；`impl` 与 `route` 双轨修订（`route_provisional` 可改路由），冲突必须登记进 `stage4_plan.md` 的「DOM 冲突修订表」。
- **4a plan 审查门**：文件清单 / PO 方法设计 / 采集状态表 / 冲突修订表 / 断言实现映射 / 阶梯自检 / 项目约定对照。
- **4b 编码**：每个定位符标来源（`page_cache/xxx#L42` / 存量 PO / codegen），缺页不许猜。

### 6.4 阶段 5 探查-修复循环

≤7 轮，每轮：
1. 跑测试（命令取 `profile.run.test_command`，不硬编码）。
2. 失败：优先读 conftest 自动保存的失败现场（`profile.paths.screenshot_dir` 下 `.png` + `.html`）。
3. **按断言三维字段自动归因**：超时 → 脚本/环境；值不对 → 产品缺陷；C 类 → 仅告警。
4. 归因为定位符/断言不符且缺 DOM 事实 → **按需采集单页**写回 `page_cache/`。
5. 修 → 重跑。
6. 用尽 → `5_verify=failed`，按 §4.3 处理。manual / semi-auto 回拨至 4 并提示 `/tw:ui-test-diagnosis`，full-auto 停在 5 并报告。

**禁放宽断言迁就实现**。

### 6.5 阶段 6 flaky quarantine 四步

识别（重跑 2–3 次）→ 隔离（标记 skip/xfail + 单独套件）→ 归因（等待/数据/环境/产品）→ 治理（修或转 issue，禁止长期挂着）。

### 7.1 五阶段与审查门

| 阶段 | key | 命令 | 域包指令 | review_gate | 产出 |
|---|---|---|---|---|---|
| 1 录制 | `1_capture` | `record-capture` | `workflows/record-driven/stages/stage1_capture.md` | none（阶段内 1e 人工核对） | `stage1_record.md` + `recorded/*.py` |
| 2 生成用例 | `2_casegen` | `record-casegen` | `.../stage2_casegen.md` | mandatory | `stage2_cases.md/.json` |
| 3 开发用例 | `3_case` | `record-dev` | `.../stage3_case_dev.md` | substep（3a） | `stage3_plan.md` + `stage3_files.md` |
| 4 执行并修复 | `4_run` | `record-run` | `.../stage4_run.md` | none | `stage4_run.log` |
| 5 代码审核 | `5_review` | `record-review` | `.../stage5_review.md` | mandatory | `stage5_review.md` |

### 7.2 各阶段关键纪律

**阶段 1 录制**
- 1-0 依赖检查（缺一即停）。
- 只录**一条正向主流程**；异常分支不录。
- codegen 命令带 `--viewport-size <profile.run.viewport>`（缺省不得回落 1280×720）。
- 后处理委托域包 `tools/record.md`：语法检查 / 引号转义 / POM 生成 / **自动复用已有登录方法**（auth fixture > LoginPage > api_login，无需人工确认）/ 补充缺失操作 / `storage_state.json` 加入 `.gitignore`（含 token）。
- `stage1_record.md` 登记流程描述 + 识别到的操作序列，供阶段 2 拆解。
- **1e 操作序列人工核对**：逐条列序号/目标/值请用户确认无遗漏；single 模式无阶段 2 拆解兜底，**不可跳**。
- 不执行 `record.md` 的 `--with-assertion` 段（断言归阶段 2）。

**阶段 2 生成用例**
- 派生模式先定：`full`（默认，完整用例集）或 `single`（只开发录制的这一条，`cases` 长度 1，`expansion_mode="single"`）。
- 流程：2-0 前置检查（`recorded/*.py` 存在且非空）→ 2a 拆解（按操作类型/页面边界/提交动作切段，场景必须能独立执行）→ 2b 三路依据（KB > DOM > 查重）→ 2c 派生（正向/边界/负面）→ 2d 挂载断言 → 2e `data_plan`（前置清理 + 后置清理 + 隔离键 + 可见性验证）→ 2f 双格式 → 2g 强制审查门。
- single 模式：跳过拆解与派生，但 §2 依据纪律与 §3.4 断言挂载照常生效（依据降为"尽力而为"，写不出标「待阶段 3 核实」）。
- 三路皆空：**不编造**，只出正向变体，`evidence.degraded=true`，md 顶部显式降级说明。

**阶段 3 开发用例**
- 3-pre DOM 准备（缓存/存量 PO 命中免采）。
- 3a plan 审查：文件清单 / PO 方法设计（定位符证据为**可核验三元组**：证据位置 / 验证了什么 / 易失效项的验证动作）/ 用例→方法映射 / **steps→方法覆盖表**（逐条 step 有归属，无归属即缺口，single 必填）/ 阶梯自检 / 项目约定对照。
- 3b 编码；3c 写 `stage3_files.md`。

**阶段 4 执行并修复**
- 7 轮探查-修复循环，归因逻辑同 8 阶段阶段 5。
- 归因为环境/真实 bug → 停止报告，**不改脚本绕过**（改了就是假绿）。

**阶段 5 代码审核**
- **必须拉起独立审核子代理**（`subagent`），不能同一上下文自审。
- 审核对象：**跑通后存活下来的最终代码**（含阶段 4 的改动）。
- 五类检查：① PO 规范 ② 断言覆盖（对 `stage2_cases.json` **逐条对账**，含 ②.5 数据准备/清理）③ 域包坑点扫描 ④ 脆弱定位符 ⑤ 过度设计（只覆盖"多写"，全部「建议」级，永不判阻塞）。
- 结论：通过 / 需修。需修 → 回拨阶段 3，重走 3→4→5 整轮，受 `rework_round > 2` 上限。

### 7.3 `--full` 的错误处理（3 类必须停 + 2 类确定性处理）

源码有两处口径：`record-auto/SKILL.md` 把"必须停下"列了 3 条；`gate-protocol §5.4` 列了 5 行。合并后按**是否需要判断力**分两类实现（"停"= 终止推进并报告，不是暂停等待输入）：

| # | 情形 | 处理 | 类别 |
|---|---|---|---|
| 1 | 阶段 2 `evidence.degraded == true` | 停止报告——依据不足的用例集不该无人确认就进入开发 | **必须停** |
| 2 | 阶段 4 归因为环境问题 / 真实 bug | 立即停止，不改脚本绕过（改了就是假绿） | **必须停** |
| 3 | 任一校验器报 ERROR | 停止报告（WARNING 不触发） | **必须停** |
| 4 | 阶段 4 七轮修复用尽仍失败 | 记录 `4_run=failed`、`current_stage` 停在 4，停止推进；**不自动回拨**，`rework_round` 不变 | 确定性处理（停止） |
| 5 | 阶段 5 存在阻塞项（结论「需修」） | **自动回拨阶段 3** 重走整轮，`rework_round += 1`，受 `> 2` 约束；超限转停止报告 | 确定性处理（回拨） |

> `rework_round > 2` **不是独立的第 5 条安全阀**，而是第 5 行的上限子约束。真正"不得跳过、触发即停"的只有前 3 条；第 4 行也是停，但属状态机可判定的确定性结果。
>
> **第 3 条的"校验器"范围**：指本阶段 Exit Gate Step 5 实际运行的那一个——8 阶段用 `validate_workflow.py --workflows-dir .claude/workflows`，录制用 `validate_record_workflow.py --workflows-dir .claude/record-workflows`，均为**非 strict**（WARNING 不触发停止）。不要把另一套校验器的结果混进来。

停止格式：
```
⛔ 全自动推进已停止：<原因>
已完成阶段：<列表>
待人工决策：<具体问题 + 相关文件:行>
继续方式：修复后调 /tw:record-<stage> 或 /tw:record-auto <feature>
```

### 9.6 `project-scan` 的域包匹配算法（新包如何被自动发现）

**没有单独的"域包注册表"**——`tw/packs/*/pack.yaml` 本身就是注册表。新建 `tw/packs/<pack_id>/pack.yaml` 后，`/tw:project-scan` 自动可见，无需改任何 L0 文件。

| 步骤 | 规则 |
|---|---|
| 1. 分端 | 混合子系统（同子系统含 web+app）必须**逐端**检测，输出「端 / 信号文件 / 命中内容 / 指向栈」 |
| 2. 取信号 | 遍历每个 pack.yaml 的 `tech.platforms` + `tech.signals`；skill 不维护信号清单，新增域包只改 pack.yaml |
| 3. 计分 | `deps_*` 命中 ×3；`files_any_of`（配置）命中 ×2；`dirs_any_of` 命中 ×1；`negative` 命中 ×(−5) |
| 4. 判定 | 总分 <3 → 不成候选；negative 使总分 ≤0 → 直接排除；最高分唯一且 ≥3 → 推荐（仍须用户确认）；最高分并列 → 列出全部由用户选，**不代选** |
| 5. 无匹配 | 有实质源码但所有候选 <3 → 「存量项目但栈未注册」：列已注册域包后停止，不生成骨架 |
| 6. greenfield | 信号全 0 且仓库近乎空（无依赖清单/无框架配置/无测试目录，或源码文件 ≤10）→ 询问目标栈，按选定 pack 定向接入，profile 标 `greenfield: true` |
| 7. 重扫 | 增量合并：检测类字段刷新；人工确认字段（`run.*`/`data_layer.*`/`kb.path`/`feedback_channel`）与正文（约定/坑点表/术语）默认保留，逐项展示 diff 由用户选 |

**配置信号的定义**：`files_any_of` 是"框架配置文件"类 glob（如 `pytest.ini`、`playwright.config.py`），按 ×2 计；`dirs_any_of` 是目录特征，按 ×1 计。不要把测试代码文件放进 `files_any_of` 冒充配置信号。

## 10. 工具链设计

### 10.1 总览

| 工具 | 路径 | 作用 | 关键模式 |
|---|---|---|---|
| 8 阶段分发器生成器 | `tw/tools/gen_dispatchers.py` | 从单一模板渲染 8 个 SKILL.md | 默认写入；`--check` 只 diff |
| HANDOFF 生成器 | `tw/tools/gen_handoff.py` | 生成项目 `HANDOFF.md` 的阶段→命令映射段 | 标记区间替换，标记外手写内容保留 |
| 8 阶段校验器 | `tw/tools/validate_workflow.py` | 状态机校验 + 域包自检 + profile 契约 + dump 契约 | 默认（配 `--workflows-dir`）/ `--check-pack` / `--check-profile-contract` / `--check-dump-contract` / `--strict` |
| 结构化产物校验器 | `tw/tools/validate_artifacts.py` | 两条工作流的用例、断言及引用检查 | `--workflow` / `--feature-dir` / `--stage` |
| 录制分发器生成器 | `tw/workflows/record-driven/tools/gen_record_dispatchers.py` | 渲染 5 个录制阶段 SKILL.md | 默认 / `--check` |
| 录制校验器 | `tw/workflows/record-driven/tools/validate_record_workflow.py` | 录制状态机校验 + 定义自检 | `--check-workflow` / `--workflows-dir` / `--strict` |

**`--strict` 的用法**：把 WARNING 升级为失败。日常 Exit Gate 用非 strict（存量历史欠账不该阻断）；**新建仓库的验收用 strict**，确保没有未声明文件（C2R/W3R/W8 全部清零）。

**`baselines/` 的定位**：仅作为 iOS 迁移期的校验输出基线存档，**没有任何脚本消费它**；重建时可以不建该目录，或在需要迁移比对时手工生成。

### 10.2 生成器设计（防漂移的核心）

**单一模板 + STAGES 参数字典**。模板中的可变点：
- `{num}` `{command}` `{title}` `{triggers}`
- `{exec_notes}`（阶段 4 把具体纪律写进分发器）
- `{gate_check_extra}` / `{step3_extra}` / `{step4_extra}` / `{closing}`（阶段 5 专用占位符，内容必须是**指向协议的指针**，不得复述协议条款）
- `{review_gate}`（"（**强制**：……）"）

护栏（注意执行范围与时机不同）：

1. **引用契约（两个生成器；默认渲染与 `--check` 都执行）**：渲染内容中出现的具体 `tw/**.md|yaml|py` 路径必须真实存在。正则 `tw/[\w./-]+\.(?:md|yaml|py)`；`<占位符>` 路径因不以扩展名结尾天然跳过。**默认渲染时失败必须 abort，不得写入**（源码的 `main()` 就是这么做的）。
2. **零耦合断言（两个生成器；默认渲染与 `--check` 都执行）**：8 阶段渲染内容不得出现 `record-workflows` / `record_state`；录制渲染内容不得出现 `.claude/workflows`。
3. **覆盖护栏（两个生成器的 `--check` 均执行）**：含 `[TW 阶段N]` 或 `[TW 录制阶段N]` 的 skill，其所在命令目录必须匹配相应生成器 `STAGES[N]` 登记的命令。

`--check` 退出码：有漂移/缺失 → 1；全部一致 → 0。

### 10.3 `validate_workflow.py` 校验项

**默认模式**（**必须显式传 `--workflows-dir <项目>/.claude/workflows`**）：
1. state.json 顶层字段、8 阶段键、status 枚举、`human_intervention` 规范。
2. `current_stage` 自洽（含阶段 5 失败时的模式分支，见 §4.3）。
3. done 阶段产出文件存在（**WARNING**，不是 ERROR——存量 feature 有历史欠账，升 ERROR 会阻断所有项目的 Exit Gate；录制校验器零存量，同场景为 ERROR。这个差异是故意的）。
4. `bypasses` ↔ `skipped` 双向对账，reason ≥5 字符。
5. `.current` 存在且指向有效 feature。
6. dashboard 头部计数与实际一致、每个 feature 已登记、`_template` 未登记。阶段状态从校验时已读入的数据计算；状态文件或阶段结构损坏时，报告 ERROR 并跳过状态分桶计数对账。

> **源码行为与重建裁决**：源码不传 `--workflows-dir` 时把"脚本位置的上两级"当作目录，也就是 plugin 自己的 `tw/`；在宿主项目裸跑会扫描 `tw/packs|protocols|templates|tools|workflows` 并报 `.current`/`dashboard` 缺失的 ERROR。
> **重建时必须修正**：省略参数 → 默认取**当前工作目录**下的 `.claude/workflows`；该目录不存在 → 直接 ERROR 并提示传 `--workflows-dir`。**禁止**回落到脚本所在目录。状态机校验（默认模式）总是传参；`--check-*` 模式不需要该参数。

**`--check-pack [dir]`**：
- C1 八槽位齐全、status 合法。
- C2 implemented 槽位、辅助能力、知识库协议的文件引用与阶段产出清单按 §5.1 校验。
- C5 pitfalls 存在。
- C2R 反向：`stages|references|tools` 下未声明的 md → WARNING；顶层未纳入扫描/豁免的目录 → WARNING；`--strict` 升级为失败。
- 健壮性：pack.yaml 为空/列表/标量时必须干净 FAIL，**不得 AttributeError 崩溃**。
- C3、C4、C6 属于正文规范，由验收套件及评审覆盖。

**`--check-profile-contract`**：
- 扫描 `skills/`、`tw/packs/`、`tw/protocols/`、`tw/workflows/` 中的 `<section>.<field>` 引用。
- 正向：引用未在模板定义 → ✗。
- 反向：模板定义但无人消费 → `[INFO]`（预留字段，不判错）。
- 排除扩展名类误匹配（`dashboard.md` 的 `md` 等）。

**`--check-dump-contract`**：
- 协议文件存在。
- 每个域包 `auxiliary.dump-page.file` 存在且正文引用 `dump-artifact-protocol.md`。
- 全域（skills + packs）不得出现裸 dump 文件名（`page_dump*.html|png|xml`、`page_source*.xml`）。

### 10.4 `validate_record_workflow.py` 校验项

**`--check-workflow`**：
- 5 槽位齐全、阶段 key 与槽位对应、command 为字符串；每个适用域包都须提供 `pack_path` 和域包级 `references` 文件，共用协议引用按 §5.6 解析。artifacts 包含状态校验器要求的产出，可声明不重复的额外相对路径。
- W3R 能力对账（WARNING）：`applies_to_packs` ↔ 域包 `auxiliary.record` 双向。
- W8 反向声明（WARNING）：域包录制子树下存在的 `*.md` 必须在 `workflow.yaml` 中声明。

**`--workflows-dir`**：
1. record_state schema：顶层字段、`workflow=="record-driven"`、5 阶段键、status 枚举、`human_intervention`。
2. `current_stage` 自洽（含 4/5 回拨 3）。
3. done 产出缺失 → **ERROR**（零存量）。
4. bypasses ↔ skipped。
5. `.current` 有效性。
6. dashboard 一致性。与 8 阶段校验器相同，校验和分桶统计共用一次读取的状态。
7. `rework_round > 2` → WARNING。

### 10.5 实现要求（给重建者）

- 所有脚本 UTF-8 输出重配置（`sys.stdout/stderr.reconfigure(encoding="utf-8", errors="replace")`）。源码中 `gen_handoff.py` 缺这一步，是已知瑕疵；重建时补齐。
- 路径推导用 `Path(__file__).resolve().parents[n]`，**不写死绝对路径**（plugin 会被安装到缓存目录）。
- `yaml.safe_load` 的结果必须做 `isinstance(dict)` 守卫（空文件返回 None）。
- 错误/警告分行收集，最后统一输出；退出码：ERROR 或无错误但 `--strict` 有 warning → 1，否则 0。
- 校验器之间**不得互相 import**（两套状态机零耦合）。
- 生成器与校验器之间也不得 import；共享的只有"文件是否存在"这类常识。

## 14. 已知风险与重建陷阱

| 风险 | 表现 | 规避 |
|---|---|---|
| 把两条工作流合并 | 状态机语义打架、审核对象错位 | 保持零耦合；只共享方法论协议文档 |
| 在 skill 里硬编码域包 | 新增域包要改 L0 | 一律走 `auxiliary` 键 |
| 在域包阶段指令里写状态 | 双写者导致状态不一致 | C3 协议约束；状态只由 Exit Gate 写（校验器不检查正文，需评审兜底） |
| 协议条款在多个文件重复 | 改一处漏一处，语义漂移 | 协议唯一真相源；域包只引用章节号 |
| 生成器模板里复述协议 | 协议变更后分发器语义过期 | 占位符只放"指向协议的指针" |
| 中文路径/编码 | Windows GBK 控制台乱码、同形近字误抄 | 全部脚本 UTF-8；非 ASCII 字面量从数据源取值，禁止从控制台转录 |
| `yaml.safe_load` 空文件 | `None.get()` 崩溃 | isinstance 守卫 |
| 路径写死 | 安装到 plugin 缓存后失效 | `Path(__file__).resolve().parents[n]` + Glob 兜底 |
| 把 dump 产物写 CWD | 阶段 4/5 找不到 | 唯一真相源 `dump-artifact-protocol.md`；校验器拦裸文件名 |
| 校验器把存量历史欠账当 ERROR | 所有存量项目 Exit Gate 被阻断 | 8 阶段 done 产出缺失保持 WARNING；录制保持 ERROR |
| `--full` 无人兜底却继续推进 | 假绿交付 | 3 类必须停，触发即终止推进（不是暂停等输入） |
| 全量硬采 DOM | token 与时间双爆 | 分级采集（缓存/存量 PO 免采），阶段 5 按需补 |
| 正向变体做笛卡尔积 | 用例爆炸、定位困难 | 只取会走不同代码分支的组合 |
| 只按英文名查重 | 漏掉中文编号命名的存量用例 | 中英双语并行查重 |
| 按旧模块猜 DB 字段 | 断言永远失败 | 先 `information_schema` 定位表 → `DESCRIBE` → 闭环验证 |

### 15.2 术语表

| 术语 | 含义 |

### 15.3 重建边界声明（重要）
